남은 개선은 무엇인가?

다음 순서는 strict deep 검색의 재현 가능한 병목과 unscoped deep의 꼬리 지연을 먼저 확인하고, SQLite parity 다섯 실패를 정리한 뒤, 독립적인 기억 품질·실제 LLM 압축·현재 앱 통합으로 넘어가는 것입니다. 영어 전체 코퍼스와 ANN 확대는 품질 및 자원 통과 조건을 먼저 충족한 뒤 진행할 과제입니다.

  1. P0 · 검색 병목: strict deep의 worker iterator·후보 로딩·거리 계산 비용과 unscoped deep p95를 새 프로세스에서 분리해 재현합니다.
  2. P1 · SQLite parity: epoch 2, flashbulb 1, semantic consolidation 1, cross-domain analogy 1의 다섯 실패를 동일 의미로 구현해 원래 assertion을 통과시키고 조용한 오판을 없앱니다.
  3. P2 · 기억 품질: 독립 holdout과 원어민 검토로 최신·오래된·삭제·선호·감정·무관 기억 침입을 평가합니다.
  4. P2 · 실제 압축: anchor/mock 수치가 아닌 실제 tokenizer·LLM으로 보존율, 환각, 부정·취소·모순, 비용과 지연을 검증합니다.
  5. P2 · 현재 앱 통합: 이미 완료된 package·Local·mmap 재시작 검증을 반복하지 않고 naia-agent와 naia-shell의 실제 호출·오류 경로를 확인합니다.
  6. P2 · 제품·확장: 위 품질과 자원 조건을 통과한 뒤 영어 전체 코퍼스와 ANN을 확장합니다.

SQLite 다섯 실패 외에도 semantic decay, associate, procedural, hubs, KG 관련 기능의 부족한 구현·검증과 SQLite backup 미지원이 남은 범위입니다.

초기 실패 11개가 최신 기본 테스트에서 사라진 사실을 전부 코드 개선의 결과로 해석할 수는 없습니다. 테스트 수·수집 범위·실행 조건이 달라졌고, 초기에는 subprocess 권한 같은 환경 관측도 있었습니다.

단계별 변화

초기 조사 · P0

기능은 연결되어 있었지만, 제품 판단에 필요한 증거가 부족했습니다

LocalAdapter 기본 경로와 한국어·아랍어 검색은 연결되어 있었지만 실제 대화 기억의 정확도·유용성에 대한 독립 평가가 부족했습니다. SQLite는 기능 parity가 완결되지 않았고, update/delete 근거는 작은 사례에 머물렀습니다. 압축 수치는 mock/anchor 기반이어서 실제 LLM 품질이나 상한으로 사용할 수 없었습니다.

평가 공백

최신·오래된·삭제된 기억, 선호 변경, 감정 기억, 무관 기억 침입을 독립 holdout으로 검증할 필요가 있었습니다.

운영 공백

패키지·재시작·update/delete·격리와 실제 앱 사용 경로를 같은 조건으로 확인해야 했습니다.

성능 공백

영어 전체 코퍼스와 ANN 확대 전, 자원 예산과 품질 게이트가 필요했습니다.

P0에서 완료한 실제 개선: 테스트별 임시 DB 격리, CLI 실행기 변경, 빈 backup 성공의 명시적 거부, 시간 fixture의 validFrom 보정, mock 압축 수치 주장의 정정을 적용했습니다.

Stage 3 · backup capability

실제로 지원하지 않는 SQLite backup을 true로 보고하던 경로를 차단했습니다

SQLite adapter는 export/import 메서드를 가지고 있지만 호출하면 unsupported 오류를 내므로, 메서드 존재만 검사하는 capability 판정은 false positive였습니다. 또한 provider가 찾던 exportBackup/importBackup 이름이 LocalAdapter의 public export/import 경로와 달랐습니다.

시점 SQLite backup 동작 판정
초기 빈 bytes/noop backup 호출이 성공처럼 보임 false positive
P0 backup 호출을 명시적 unsupported 오류로 거부 빈 성공 차단
stage 3 호출 거부와 supportsBackup() false를 함께 노출 SQLite 미지원 명시

변경된 동작

  • MemorySystem은 backupSupported !== false이고 export/import 두 함수가 실제 callable일 때만 backup을 지원합니다.
  • SQLite는 capability를 명시적으로 false로 보고하며 직접 backup 호출도 기존의 명시적 unsupported 오류를 유지합니다.
  • provider는 Local public backup을 system에 위임하고, 백업에 한해서만 optional gate를 반영합니다.
  • public API에는 NaiaMemoryProvider와 options 타입을 노출했습니다.

확인된 결과

  • Local provider encrypted roundtrip과 restart 통과
  • wrong password는 reject하고 target 데이터는 보존
  • SQLite capability false, backup 거부 후 기존 데이터 사용 가능
  • legacy 외부 provider는 optional gate가 없어도 exportBackup/importBackup 두 함수가 있으면 true
  • exportBackup/importBackup 중 하나라도 누락·비함수면 false
  • explicit false gate와 gate true인데 메서드가 누락된 경우도 false
  • 백업 gate가 다른 capability 판정에 영향을 주지 않음
  • compiled package root import과 public provider/options type export 통과
  • mmap strict reopen(worker built JS) 통과

stage 3 집중 검증은 3개 파일·50개 테스트 모두 통과했습니다. 집중 로그 파일명은 luna-focused.log입니다. 패키지 공개·Local backup·재시작·mmap reopen 검증은 완료되었고, 실제로 남은 제품 통합은 naia-agent와 naia-shell입니다.

성능 결과의 의미와 한계

stage 1과 stage 2는 같은 제품 경로를 다룬 별도 실험이지만 baseline·실행 수집이 다릅니다. 따라서 아래 수치는 각 단계 안에서만 before/after로 읽어야 합니다.

각 단계는 3쌍·6회 실행이며, 각 실행의 p50/p95를 산출한 뒤 3개 실행값의 중앙값을 표시했습니다. 호출을 모두 합친 백분위가 아닙니다. 두 실험은 100k synthetic DB, warm cache, shared host 조건이므로 production workload와 cold-cache 결과를 보장하지 않습니다. 각 단계의 735회는 반복 대응 호출이며 독립 질의 수가 아닙니다.

strict / unscoped

strict는 프로젝트 범위 제한을 적용한 검색이고, unscoped는 프로젝트 제한 없이 검색하는 경로입니다.

surface / deep

surface는 빠른 회상 모드, deep은 심층 회상 모드이며, 표는 같은 모드의 변경 전후 지연을 비교합니다.

p50 / p95

p50은 가운데 지연이고, p95는 느린 쪽 5%가 시작되는 꼬리 지연입니다.

일정 추정은 하지 않습니다. 우선순위는 제품 위험과 검증 의존 순서로 정했고, 각 항목은 결과를 판정할 수 있는 조건으로 적었습니다.

  1. P0
    strict deep 병목과 unscoped deep p95 해소

    새 프로세스에서 strict deep의 worker iterator, 후보 BLOB 로딩, 거리 계산, IPC/final facts 비용과 unscoped deep p95를 분리 측정합니다. mmap은 실제 적용값과 RSS/매핑 자원을 확인하고, paired p50·p95가 안정적으로 개선되며 ID·순서·점수·DB hash와 unscoped 동작을 보존할 때만 기본 경로 승격을 검토합니다.

  2. P1
    SQLite parity 남은 5개 실패 해소

    5개 실패는 epoch 2, flashbulb 1, semantic consolidation 1, cross-domain analogy 1의 네 유형입니다. 각 기능을 Local과 동일한 의미로 구현하고 원래 assertion을 통과시킵니다. 동일 입력의 save·restart·recall, update/archive, project isolation이 SQLite에서도 재현되고 전체 parity suite가 통과해야 합니다.

  3. P2
    독립적인 기억 품질 평가

    중복되지 않은 holdout과 원어민 검토로 최신 사실, 오래된 사실, 삭제·취소, 선호 변경, 감정 기억, 무관 기억 침입을 평가합니다. no-memory·simple search· Naia와 ablation을 같은 입력·예산에서 비교하고 정확도, stale/deleted 사용, token·cost·latency와 신뢰구간·실패 원인을 함께 보고합니다.

  4. P2
    실제 LLM 기반 압축

    입력에 답을 심은 anchor/mock 조건을 제거하고 실제 tokenizer·LLM으로 uncompressed/basic/rolling/LLM을 비교합니다. 이름·사실·시간·부정·취소· 모순 보존, 환각, token 절감, 비용과 지연을 함께 통과시켜야 합니다.

  5. P2
    현재 앱 통합

    이미 완료한 compiled package root import, public provider/options type, Local backup roundtrip·wrong-password 보존·restart, mmap strict reopen을 반복하지 않고 naia-agent와 naia-shell의 실제 호출·오류 경로를 확인합니다.

  6. P2
    영어 전체 코퍼스와 ANN 확장

    영어 전체 코퍼스 실행과 ANN 승격은 독립 품질 평가와 자원 예산, 검색 결과 보존, 재현 가능한 실패 분류가 통과된 뒤에 진행합니다. 작은 preflight나 synthetic throughput을 전체 완료의 대리 지표로 사용하지 않습니다.

각 후속 검증에서도 subprocess 권한·IPC·openssl 같은 환경 관측과 코드 실패를 별도 분류합니다. 최신 기본 suite의 통과만으로 초기 실패 전체가 코드로 해결됐다고 결론내리지 않습니다.

현재 결론

확인된 성과

strict project-scope vector 후보 처리는 같은 결과를 보존하면서 빨라졌고, mmap은 기본값 0인 opt-in 설정으로 정리되었습니다. backup capability는 실제 callable 여부와 명시적 false를 반영하며, Local public provider backup 경로가 동작하도록 맞춰졌습니다. compiled package root import, public provider/options type, Local encrypted roundtrip·wrong-password target 보존·restart, mmap strict reopen도 검증했습니다. 최신 기본 테스트 1,473개는 통과했습니다.

아직 입증하지 못한 범위

SQLite는 아직 full parity가 아니며 epoch, flashbulb, semantic consolidation, cross-domain analogy의 5개 실패가 남아 있습니다. semantic decay, associate, procedural, hubs, KG도 부족한 구현·검증이 남은 범위입니다. mmap은 기본 성능 개선으로 확정되지 않았고, 실제 대화 기억 품질·실제 LLM 압축·현재 앱 통합은 별도 증거가 필요합니다. 실제 앱 통합에서 남은 표면은 naia-agent와 naia-shell입니다.
