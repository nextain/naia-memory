# Naia Memory 프로젝트 범위 검색 성능 개선

작성일: 2026-09-05 · Luna max 구현 / Astra 단계별 검토 · 상태: 첫 성능 개선 단계 완료 · 로컬 작업 트리

SQLite에서 프로젝트 범위를 지정한 벡터 검색을 수정했다. 후보 전체를 메인 스레드로 복사해 정렬하던 부분을 워커 내부의 상위 후보 선택으로 바꿨다. 이 문서는 같은 10만 건 DB의 변경 전후 비교와 정확성 검증을 기록한다. 기존 6주 추정은 철회했으며, 측정과 통과 조건을 기준으로 다음 단계를 정한다.

## 측정 결과

**프로젝트 범위 검색의 중앙 지연시간(p50)이 surface 36.7%, deep 53.8% 줄었다.** 세 쌍 모두 이 두 경로의 p50과 p95가 감소했다. 아래는 각 실행에서 구한 백분위수 세 개의 중앙값이다. 전체 180개 표본을 합친 백분위수가 아니며, 변화율은 두 중앙값의 비율로 계산했다.

| 검색 경로 | p50 변경 전 → 후 | p50 변화 | p95 변경 전 → 후 | p95 변화 |
|---|---:|---:|---:|---:|
| 프로젝트 범위 · surface | 357.24 → 226.18ms | 36.7% 감소 | 459.13 → 270.20ms | 41.1% 감소 |
| 프로젝트 범위 · deep | 2176.23 → 1006.25ms | 53.8% 감소 | 2363.07 → 1221.44ms | 48.3% 감소 |
| 전체 범위 · surface | 6.86 → 6.81ms | 0.8% 감소 | 25.66 → 25.35ms | 1.2% 감소 |
| 전체 범위 · deep | 88.78 → 91.06ms | 2.6% 증가 | 139.84 → 141.55ms | 1.2% 증가 |

반복 실행 사이의 범위도 함께 기록한다. 단위는 ms다.

| 검색 경로 | 변경 전 p50 범위 | 변경 후 p50 범위 | 변경 전 p95 범위 | 변경 후 p95 범위 |
|---|---:|---:|---:|---:|
| 프로젝트 범위 · surface | 318.01–408.69 | 225.71–244.30 | 396.19–460.24 | 254.83–299.94 |
| 프로젝트 범위 · deep | 2094.57–2290.91 | 964.97–1053.27 | 2337.60–2587.90 | 1160.92–1222.54 |
| 전체 범위 · surface | 6.56–9.91 | 6.09–7.42 | 25.56–26.55 | 24.21–25.99 |
| 전체 범위 · deep | 80.04–90.47 | 74.69–91.61 | 107.39–143.40 | 124.40–144.13 |

전체 범위 deep는 p50 중앙값이 2.6%, p95 중앙값이 1.2% 증가했다. 세 번째 쌍의 p95 증가는 15.8%이고, 첫 번째 쌍의 최댓값도 150.16 → 188.79ms로 증가했다. 변동 범위가 겹치는 공유 호스트의 세 쌍 측정만으로 원인을 단정할 수 없으며, 대조 경로의 회귀 가능성은 후속 확인 대상으로 남긴다. 모든 검색 경로가 개선됐거나 영향이 없다고 주장하지 않는다.

**735회 A/B 대응 호출에서 결과 ID·순서·relevanceScore가 정확히 일치했다.** 이는 `3쌍 × (4경로 × 60회 + 추가 probe 5회)`이며, 서로 다른 질의 735개나 의미 정확도 100%를 뜻하지 않는다. 질의 문자열은 15개를 반복한다. 각 일반 측정은 결과 10개를 반환했고, 없는 프로젝트 probe는 빈 결과였다. 모든 실행 전후 DB 해시는 다음 값으로 유지됐다.

```text
6825406b56e917362292267a89db35a1cd7a244aaed13d1ec277f4928aa9c673
```

## 비교 조건과 재현 범위

A는 성능 수정 직전의 실제 작업 트리 사본이다. 앞선 P0 수정과 기존 미커밋 변경을 포함하므로 깨끗한 HEAD가 아니다. B는 이번 성능 수정 후 소스다. HEAD는 `80b95b4b75c8e913e83e660ea6255304edb5a197`이며, 이번 변경만의 patch와 A/B 소스 사본을 별도로 보존한다.

| 조건 | 값 |
|---|---|
| 환경 | i9-13900K, Node 26.7.0, SQLite 3.53.1, sqlite-vec 0.1.9, Linux |
| 데이터 | 합성 사실 100,000개, hot 10,000개, 결정론적 384차원 임베딩 |
| 프로젝트 분포 | 대상 90,000개/hot 9,000개, 외부 9,000개/hot 900개, 미지정 1,000개/hot 100개 |
| 측정 경계 | `MemorySystem.recall`, topK 10, strict/unscoped 각각 surface/deep |
| 질의 | 15개 질의로 워밍업 후 같은 질의를 네 번 순환해 경로당 60회 측정 |
| 반복 | 서로 다른 프로세스로 A1 → B1 → B2 → A2 → A3 → B3 직렬 실행 |
| 경로 순서 | 1·3쌍 정방향, 2쌍 역방향 |
| 추가 확인 | 프로젝트 미지정 surface/deep, 외부 프로젝트, crossProject, 없는 프로젝트의 probe 5개 |

각 실행 전후 사실·FTS·벡터 테이블 수, 프로젝트 분포, generation, DB 전체 SHA-256, WAL을 검사한다. 여섯 실행에 동일한 하네스를 사용하고 A/B 각각 소스 해시가 반복 사이에 바뀌지 않았는지 집계 때 검증한다. 정확히 네 경로·경로당 60개 표본·다섯 probe가 있는지, 환경과 고정 metadata가 같은지도 검사하며 지연 요약을 원시 값으로 재계산한다.

seed 기록에 남은 하네스 해시는 최종 A/B 하네스와 다르다. 원래 seed 하네스 파일은 보존하지 못했으므로 생성 절차의 바이트 단위 복원을 주장하지 않는다. 보존된 최종 하네스는 명시된 데이터 규칙으로 새 DB를 생성하며, 재실행 내부에서 seed DB의 불변성과 A/B 결과 동등성을 검사한다. 원실행 seed metadata와 DB 해시는 보존했다.

## 구현과 정확성

strict scope 분기의 SQL, 프로젝트·이력 필터, 후보 제한 `topK * 10`은 유지했다. [SQLite adapter](../../src/memory/adapters/sqlite.ts)가 SQL과 질의 벡터를 워커에 전달하고, [워커](../../src/memory/adapters/sqlite-worker.ts)가 행을 순회하며 [exactVectorTopN](../../src/memory/adapters/sqlite-vector-search.ts)에서 최대 힙으로 필요한 후보만 유지한다. 정상 입력에서는 후보 전체 BLOB의 스레드 간 전달과 전체 정렬을 없앤다. 벡터 전체를 읽고 거리를 계산하는 작업은 남아 있다.

기존 결과를 유지하기 위해 저장 벡터의 Float32 값, 질의의 JavaScript Number, 차원별 누적 순서, `sqrt` 후 거리, 동점일 때의 원래 스캔 순서를 보존했다. NaN·Infinity 거리나 음수·비정수 등 특수 limit에는 기존 전체 정렬과 `slice` 동작으로 돌아간다. 이때 새 SQL iterator로 다시 순회해 실행 중인 statement의 재사용 문제를 피한다.

[거리·상위 후보 테스트](../../src/memory/__tests__/sqlite-vector-search.test.ts) 8개는 기존 거리 계산과 stable full sort를 기준으로 동점, sqrt 반올림, query 정밀도, 특수 limit, 비유한 거리 등을 비교한다. [SQLite smoke](../../src/memory/__tests__/sqlite-smoke.test.ts)에 추가한 테스트는 FTS가 맞지 않는 고유 질의로 벡터 경로를 강제하고 프로젝트 격리와 active hot/cold·superseded·archived의 surface/deep/history 처리를 확인한다.

## 단계별 결정과 검토

| 단계 | 결정 및 개선 |
|---|---|
| 병목 선정 | Luna max가 strict scope에서 전체 벡터를 복사·정렬하는 비용을 지목했다. Astra는 기존 거리·동점·필터 의미를 유지하는 조건으로 워커 내부 exact top-N을 수용했다. |
| 구현 검토 | Astra의 수치 경계와 lifecycle 검증 요구를 반영했다. 특수 limit·비유한 거리에는 기존 정렬로 복귀하고, 고유 질의로 실제 벡터 경로를 검사했다. 소스와 빌드된 JS의 helper 로딩도 별도로 확인했다. |
| 측정 계약 | Astra가 직렬 A/B·고정 DB·소스 해시·반복 순서를 검토했다. 요구에 따라 집계의 표본 수·환경 일치·요약 재계산 검사를 강화하고 RSS 해석과 seed 하네스 보존 한계를 명시했다. |
| 최종 결과 | Astra가 원시 6개를 경량 재집계해 저장된 summary 전체와 정확히 일치함을 확인했고, 보존 파일 32개의 해시도 검증했다. 소스·로그·문서 검토 후 이번 로컬 strict scope 성능 개선 단계를 수용했다. 필수 코드·수치 수정은 없으며 대조 경로의 회귀 가능성은 후속 확인 대상으로 남겼다. |

실행과 로그 수집은 부모 에이전트가 담당한다. Astra의 검토는 소스·원시 기록을 읽는 방식이며 검토자 자신의 런타임 실행은 아니다(`runtime_observed: false`). 정식 review-preflight는 기존 비추적 `.cache/tools/trec_eval-ba38899/`를 unsafe로 판정해 종료 코드 1로 끝났다. 그 경로는 보존했다. 사용자 지정 검토를 공식 review-pass 인증으로 표현하지 않는다.

부모는 소스 아카이브 A의 110개·B의 112개 파일 해시, 보존 기록, 보고서 로컬 링크 42개도 대조했다. 기존 사용자 변경인 `src/memory/index.ts`와 역사적 `compact-compression.json`의 시작 해시는 유지됐다. 이번 완료는 검토된 첫 성능 개선 범위이며 SQLite 기능 동등성이나 전체 연구 완료가 아니다.

SQLite 전체 검사의 남은 실패는 epoch 2개, flashbulb 1개, semantic consolidation 1개, cross-domain analogy 1개다. 해당 검사의 종료 코드는 1이며 실패를 제외하거나 통과로 바꾸지 않았다. 기본 검사의 9개 증가는 거리 oracle 8개와 벡터 lifecycle smoke 1개다. 앞선 제한 환경의 기본 검사 9개 실패가 사라진 현상은 환경 변경 후 기준 검사에서도 재현되므로 검색 최적화의 성과로 계산하지 않는다.

## 해석의 한계와 다음 단계

이 비교는 합성 임베딩·워밍업 후 로컬 회상 지연과 결과 보존을 확인한다. 실제 대화의 기억 정확도, 실제 임베더·LLM 비용, 콜드 캐시, 다중 클라이언트 부하를 입증하지 않는다. 60개 표본에서 사용한 p99 계산은 최댓값과 같으므로 안정적인 꼬리 지연 추정으로 사용하지 않는다. 호스트는 공유 데스크톱이며 전용 CPU를 예약하지 않았다.

원시 RSS와 maxRSS는 DB 전체 해시 계산의 Buffer와 앞선 검색 경로의 메모리 이력을 포함하는 프로세스 값이다. 경로별 검색 메모리나 heap 개선율로 해석하지 않는다. lifecycle 데이터는 별도 정확성 테스트에 있고 성능 DB의 모든 사실은 active다.

후속 단계는 다음 완료 조건으로 진행한다. 주 단위 일정은 산정하지 않는다.

| 순서 | 다음 작업 | 완료 조건 |
|---|---|---|
| 1 | strict deep에 남은 전체 벡터 스캔과 후속 후보 로딩 비용 분리 | 같은 고정 DB에서 각 구간 비용을 측정하고 다음 병목을 선택. 대조 경로인 unscoped deep p95 증가도 통제된 반복으로 확인. 정확성·scope 조건을 Astra가 확인한 뒤 Luna max가 수정 |
| 2 | 선택한 병목의 두 번째 개선 | 같은 기준 소스·DB의 반복 A/B에서 ID·순서·점수 유지, 기본 검사 및 빌드 동작 통과, 대조 경로의 변화도 보고 |
| 3 | SQLite 기능 격차를 독립적으로 해결 | 남은 parity 5개와 backup 지원 판정을 호출자 영향별로 수정하고 지원 표 갱신 |
| 4 | 실제 기억 품질 평가 | 독립 사례에서 기억 갱신·삭제 재노출·최종 답변 정확성을 분리 측정. 실제 모델 실행은 비용·데이터 조건 확정 후 수행 |
