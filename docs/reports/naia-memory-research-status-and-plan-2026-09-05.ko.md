# Naia Memory 연구 현황 및 개선계획

작성일: 2026-09-05 · 대상: 내부 연구·개발 의사결정

이 문서는 개선 전 조사 시점의 상태와 연구계획을 보존한다. 같은 날 진행한 Luna max 구현·Astra 단계별 검토의 변경 사항은 [P0 실행 기록](naia-memory-p0-execution-2026-09-05.ko.md), 첫 검색 최적화는 [성능 개선 실행 보고서](naia-memory-performance-stage-2026-09-05.ko.md), 후속 SQLite 읽기 최적화는 [두 번째 성능 개선 보고서](naia-memory-performance-stage2-2026-09-05.ko.md), 최신 백업 경로와 검사 결과는 [3단계 보고서](naia-memory-stage3-2026-09-05.ko.md)에 기록한다.

## 1. 현재 판단

최신 후속 작업은 [단계 3 기록](naia-memory-stage3-2026-09-05.ko.md)을 따른다. 2단계 mmap의 기본 활성화는 혼합된 성능 결과로 보류하고, 백업 지원 판정·provider 호출·패키지 공개 export 결함을 수정했다. 수정 후 기본 테스트 1,473개, 타입 검사와 빌드 패키지 백업 검증은 통과했으며 SQLite parity 5개는 별도 과제로 남는다. 다음 성능 실험은 모드별 새 프로세스에서 worker 비용과 대조 경로의 꼬리 지연을 분리한다. 아래 조사 시점의 판단과 구분한다.

Naia Memory는 로컬 기억 엔진의 구현과 대규모 검색 실험에서 진전이 있다. 한국어·아랍어 MIRACL 전체 코퍼스 검색을 완료했고, SQLite의 10만 건 저장·검색 성능을 개선했으며, 사실 갱신 시 오래된 값과 중복 표현을 정리하는 결함을 수정했다. 실험 입력·실행 환경·판정 결과를 추적하는 평가 도구도 상당 부분 갖췄다.

다음 연구의 핵심은 **실제 대화에서 기억이 정확히 바뀌고, 필요할 때 유용하게 회상되는지 검증하는 것**이다. 대규모 문서 검색의 좋은 점수만으로 장기 기억의 효용을 설명하기 어렵다. 최근 기억 갱신·삭제 비교는 언어당 서로 다른 사례가 3개뿐이고, 감정 연상·경험에 따른 선호·장기 재생의 효용은 검토한 최신 자료에서 충분히 입증되지 않았다.

개선은 **현재 기준 측정 → 병목 수정 → 정확성·성능 재검증 → 다음 실패 원인 선정** 순서로 바로 진행한다. 독립 사례 확보와 대화 전체 흐름의 비교 평가는 별도 연구 단계로 이어간다. 영어 3,289만 문서 전체 실행과 추가 평가 인프라는 이 순서 뒤에 둔다. 기존 6주 추정은 실행 근거가 부족해 철회한다.

| 평가 영역 | 현재 판정 | 다음 의사결정에 필요한 증거 |
|---|---|---|
| 기본 LocalAdapter | 구현·제품 연결 기록 있음 | 현재 배포 후보에서 저장→재시작→회상까지 확인 |
| 대규모 다국어 문서 검색 | 한국어·아랍어 전체 실행 완료 | 같은 임베더 기준선과 Naia 기능의 기여 분리 |
| 기억 갱신·삭제 | 결함 수정과 소규모 개선 관측 | 독립 보유셋, 언어별 실패율, 원인별 추적 |
| SQLite 고성능 경로 | 저장·검색 성과 있음, 기능 미완성 | 지원 기능 명세와 테스트 실행 문제 해결 |
| 요약·컨텍스트 압축 | 모의 실험 있음 | 실제 LLM의 사실 보존·환각·비용 측정 |
| 인지적 기억·개인화 | 수식·구성요소 검증 중심 | 장기 대화에서 유용성·오회상·선호 갱신 평가 |
| 경쟁력·출시 완료 주장 | 범위를 제한해야 함 | 독립 평가와 현재 제품 버전의 검증 기록 |

## 2. 조사 범위와 기준

로컬 브랜치 `feat/memory-bench-harness-and-fixes`, HEAD `80b95b4`를 기준으로 코드, 요구사항, 진행 기록, 연구 보고서, 주요 JSON 결과를 대조했다. 마지막 로컬 커밋은 8월 28일 제품 설명 문서이며, 주요 최신 실험 기록은 8월 25일까지 확인했다. 이것만으로 이후 연구가 중단됐다고 판단하지 않는다.

원격 GitHub 이슈·PR 조회는 네트워크 연결 실패로 완료하지 못했다. 추적 브랜치 대비 로컬 1커밋 선행이라는 정보도 로컬 Git 상태이다. 미커밋 변경이 존재하므로 이번 테스트는 순수한 HEAD 재현이 아닌 **현재 작업 트리 검사**다. 특히 `src/memory/index.ts`의 생성자·임베딩 공급자 export 추가는 기존 미커밋 변경이며, 릴리스 완료로 간주하지 않았다.

이번 작업에서는 보고서를 작성하고 제한된 로컬 검사를 실행했다. 전체 코퍼스 재실행, 유료 모델 호출, 경쟁 서비스 실행, 제품 배포는 수행하지 않았다. naia-agent·naia-shell 연결은 8월 24일 통합 보고서의 과거 증거를 사용했으며, 다른 프로젝트의 현재 코드를 재검증한 결과는 아니다. 이하 내부 근거의 경로는 ADK 루트 기준이다.

## 3. 연구가 어디까지 진행됐는가

### 3.1 진행 흐름

| 시기 | 주요 작업 | 현재 해석 |
|---|---|---|
| 4~5월 | LoCoMo·한국어 AI Hub 평가, 기본 엔진 개선 | 초기 검색·답변 품질의 문제를 드러낸 기준 기록 |
| 7월 | 10만 건 성능, 컨텍스트 압축, 기억 감쇠 실험 | 저장 성능과 인지 구성요소를 각각 측정하기 시작 |
| 8월 13~22일 | 구조화 사실, 대체 이력, 중복 정리, 삭제 검증, SQLite 배치 쓰기, HNSW 평가 | 실제 엔진 결함 수정과 평가 방법 정비가 함께 진행 |
| 8월 23~25일 | 한국어·아랍어 MIRACL 전체 실행, 영어 소스·배치 사전검증, 비교 엔진 실행 증거 강화 | 검색 규모 증거가 확대됨. 독립 기억 사례 확보는 여전히 과제 |
| 8월 28일 | 제품 질문 중심 설명 문서 | 설명은 개선됐으나 상태 인덱스와 요구사항에는 갱신 지연이 남음 |

4월 LoCoMo 보고서는 6개 대화·885문항에서 답변 정확도 12.2%를 기록했다. 5월 AI Hub 재분석은 키워드 기반 recall@5 38.4%, 극성을 고려한 recall@20 62.8%를 기록했다. 서로 다른 지표·데이터·구현의 수치이므로 하나의 상승 추세로 연결할 수 없다. 이 과거 결과를 현재 성능으로 인용해서도 안 된다. 다만 **검색 후보에 정보가 있다는 것과 최종 답변이 맞는다는 것을 따로 측정해야 한다**는 연구 과제는 남아 있다. [E01, E02]

### 3.2 대규모 검색: 한국어·아랍어 완료, 영어는 사전검증

| 항목 | 한국어 | 아랍어 |
|---|---:|---:|
| 전체 코퍼스 문서 수 | 1,486,752 | 2,061,414 |
| 평가 질의 수 | 213 | 2,896 |
| nDCG@10 | 0.6526 | 0.7432 |
| Recall@100 | 0.9233 | 0.9628 |
| Success@1 | 0.5962 | 0.7006 |
| 기록된 질의 평균 지연 | 약 202ms | 약 1,005ms |

이 값들은 저장된 JSON과 보고서를 대조했다. 한국어 nDCG@10은 기록에 고정된 MIRACL BM25+mDPR 기준 0.609보다 0.0436 높다. 다만 동일 환경에서 최신 경쟁 모델들을 다시 실행한 비교가 아니다. 한국어·아랍어 점수의 차이도 언어별 질의 난도가 달라 언어 간 우열로 해석하지 않는다. [E03, E04]

검색 경로는 multilingual-e5-large 기반 임베딩과 Qdrant exact cosine이다. MIRACL은 문서 검색 평가이며, E5 모델 카드에는 MIRACL 학습 분할을 미세조정에 사용했다고 명시돼 있다. 따라서 이 결과는 데이터셋 계열을 처음 접한 모델의 성능이나 Naia 고유의 기억 갱신·감쇠 기여를 증명하지 않는다. 공식 자료: [MIRACL](https://github.com/project-miracl/miracl), [multilingual-e5-large 모델 카드](https://huggingface.co/intfloat/multilingual-e5-large).

아랍어 실행은 완료 후 Qdrant를 정지한 것으로 기록돼 있다. 현재 살아 있는 컬렉션을 재검증한 결과는 아니며, 보존된 결과와 실행 기록의 증거로 취급한다. 한국어·아랍어 exact 검색 지연은 기본 LocalAdapter나 SQLite surface/deep 지연과 측정 경로가 다르다.

영어는 전체 32,893,221문서의 소스 식별을 마쳤고, 길이별 7,168문서와 64질의로 임베딩 경로를 사전검증했다. 전체 영어 검색 완료 산출물은 확인되지 않았다. [E05]

| 영어 사전검증 | 개별 처리 | 패딩 배치 |
|---|---:|---:|
| CPU 처리량 | 10.3947 docs/s | 4.1476 docs/s |
| 표본 내부 nDCG@10 | 0.983664 | 0.985295 |

배치 처리량은 개별 처리의 0.399배로 **60.1% 감소**했다. top-10 결과 집합 Jaccard는 0.7382이고, 장문에서 벡터 차이가 커졌다. 높은 표본 nDCG만으로 동등성이나 영어 전체 품질을 판정할 수 없다.

자원 규모도 크다. 표본 처리량을 단순 선형 외삽하면 임베딩만 개별 처리 약 36.6일, 현재 배치 약 91.8일이다. 이는 실제 완료시간 예측이 아니며 쓰기·색인·재시도 등은 제외한 계산이다. 1,024차원 float32 벡터 자체만 약 134.7GB가 필요하다. 전체 실행에 앞서 처리 방식과 연구상 이득을 확인할 이유가 충분하다.

### 3.3 저장·검색 성능: 개선은 확인되지만 제품 전체 성능은 별도

아래 수치는 8월의 과거 기록이다. 9월 5일에는 프로젝트 범위를 지정한 strict 검색의 병목을 별도로 수정하고, 같은 10만 건 DB에서 변경 전후 3쌍을 측정했다. 최신 결과와 조건은 [성능 개선 실행 보고서](naia-memory-performance-stage-2026-09-05.ko.md)에 있다. 검색 범위·질의·실행 환경이 다르므로 아래 값과 직접 상승·하락 추세로 연결하지 않는다.

8월 22일 SQLite 실험은 같은 틱의 upsert를 최대 1,000건씩 워커 트랜잭션으로 묶고, 커밋 후 Promise를 완료하도록 개선했다. 같은 머신의 10,001건 전후 비교에서 처리량은 6,563 → 13,746~14,051 facts/s로 2.10~2.14배 늘었다. 이 범위가 해당 수정의 효과를 설명하는 비교다. [E06]

| 8월 10만 건 기록 | 측정값 |
|---|---:|
| surface p50 / p95 | 4.04 / 5.57ms |
| deep p50 / p95 | 38.53 / 48.82ms |
| 주입 처리량 | 16,848 facts/s |
| RSS / DB 파일 | 376.4 / 220.8MB |

조건은 i9-13900K, Node 26.3.0, 결정론적 384차원 임베더, hot 1만 건, 질의 300개다. 합성 임베딩 조건에서의 저장·검색 성능으로, 실제 임베딩 생성이나 LLM 답변 지연을 포함하지 않는다. 결과의 precision 값도 실제 대화의 의미 정확도로 바꿔 인용할 수 없다. 현재 원시 성능 기록은 `dirty: true`여서 재현할 때 코드 변경분까지 보존해야 한다.

HNSW는 언어당 10만 건, 206개 양성 질의, 3회 색인 구축에서 `m=128`, `efConstruction=800`, `ef=2048`이 한국어·영어 모두 exact 대비 기준을 통과했다. 그러나 영어는 번역된 합성 사례이고, 같은 평가 자료에 대한 설정 탐색이며, 구축 비용·색인 크기·RSS·동시 처리량이 충분히 평가되지 않았다. 제품 설정으로 승격하기 전에 이 비용을 측정해야 한다. [E07]

### 3.4 기억 갱신·삭제: 개선 기전은 보이지만 일반화 근거가 부족

8월 20일에는 새 사실이 기존 정본과 중복될 때 오래된 모순 사실이 활성 상태로 남는 결함을 수정했다. 8월 21일 비교에서는 중복 표현을 함께 보관 처리하는 개선 후 삭제 대상 재노출이 6/36 → 1/36으로 줄고, 최신 사실 회상은 24/36을 유지했다. [E08, E09]

해당 비교의 단위는 **한국어·영어·일본어 각각 생성 사례 3개 × 4회 반복**이다. 엔진당 36회 실행이지만 서로 다른 사례는 총 9개다.

| 엔진 | 최신 사실 @K | 오래된 사실 노출 | 삭제 대상 재노출 |
|---|---:|---:|---:|
| Naia | 24/36 | 3/36 | 1/36 |
| Mem0 | 23/36 | 0/36 | 0/36 |
| Hindsight | 36/36 | 18/36 | 6/36 |
| Letta | 29/36 | 0/36 | 1/36 |

이 표는 실패 유형을 이해하기 위한 관측이다. Letta는 순위 검색 대신 persona를 제외한 전체 core state를 노출하므로 공통 검색 순위표로 사용할 수 없다. 생성·판정에 같은 모델 계열이 참여한 편향도 배제되지 않았다. Naia의 남은 삭제 실패는 한국어 1/12이며, 이후 같은 사례의 성공 반복으로 정식 실행의 실패를 지워서는 안 된다.

Graphiti는 실행 중인 비교 대상의 버전·모델·구성 식별을 강화했지만, 8월 23일 v2 캠페인에는 오래된 검색 결과 때문에 `DO_NOT_SCORE`가 남아 있다. 8월 24일 실행 증거 검토도 품질 우위를 주장하지 않는다. 평가 장치 완성과 실제 비교 성공을 구분해야 한다. [E10]

여기서 삭제 지표는 지정된 기억이 이후 회상에 다시 노출되는지를 본다. 저장 매체에서 물리적으로 제거됐음을 검증하는 지표는 아니다.

### 3.5 압축과 인지 연구: 주장 정정과 실제 모델 평가가 필요

8월 24일 제품 보고서의 사실 보존율 90%, 요약 비율 16.5%는 실제 LLM 측정으로 해석하면 안 된다. 원본 `compact-bench.ts`의 C 경로는 **정답 anchor 목록을 직접 참조하는 모의 요약기**다. 실제 모델의 사실 보존·환각·비용·지연을 측정하지 않았다. 90%를 실증된 상한으로 부르는 것도 부적절하다. 입력 창과 전체 anchor 분모의 범위도 다시 맞춰야 한다. [E11, E12]

같은 합성 예제의 기본 요약은 사실 보존 30%, rolling summary는 50%로 기록돼 있다. 이것 역시 한 예제의 키워드 보존 지표이며, 토큰 수는 문자 수를 4로 나눈 추정치다. 실제 다국어 토큰 예산이나 답변 품질로 일반화하지 않는다.

7월 인지 벤치는 중요도·회상 횟수에 따라 감쇠 수식이 어떻게 움직이는지 보여준다. 재생 없이 180일이 지나면 중요한 기억도 기본 활성 회상에서 빠지는 결과가 있다. 이는 보관 상태 전환에 대한 결정론적 관측이며 데이터 소실이나 사용자 경험 평가가 아니다. **재생과 재응고가 이 현상을 실제 대화에서 어떻게 개선하는지** 후속 검증이 필요하다. [E13]

감정 점수·연관·감쇠 구성요소의 존재와, 상황에 맞는 감정 연상·경험 기반 선호가 유용하다는 증거는 별개다. 개선 실험에서는 불필요한 과거 기억의 개입도 함께 평가해야 한다.

## 4. 구현·문서·검증의 남은 간극

### 4.1 SQLite는 기본 엔진과 기능이 같지 않다

개선 전 조사 시점의 `src/memory/adapters/sqlite.ts`에는 `decay`, `associate`, procedural 학습, epoch 저장, `consolidate`, `export`, `import` 등이 0·빈 값 반환 또는 빈 함수로 남아 있었다. 특히 내보내기가 빈 바이트 배열을 반환하는 식의 동작은 호출자가 완료로 오해할 여지가 있었다. 기본 LocalAdapter와 같은 기능을 갖췄다는 전제는 성립하지 않는다. [E14]

같은 날의 후속 개선에서는 SQLite `export/import`를 명시적인 미지원 오류로 바꿨다. 그 밖의 지원 범위와 남은 제한은 [SQLite 지원 범위 표](naia-memory-sqlite-support-matrix-2026-09-05.ko.md), 변경 후 검사는 [P0 실행 기록](naia-memory-p0-execution-2026-09-05.ko.md)에 기록했다.

우선 지원 기능 표를 만들고, 미지원 호출은 명시적인 기능 확인이나 오류로 드러내는 편이 적절하다. SQLite 기능 전체를 한 번에 구현하기보다 실제 제품이 필요로 하는 저장·회상·갱신·재시작 경로부터 검증한다.

### 4.2 진행 인덱스가 최신 증거를 충분히 반영하지 못한다

`process-status.json`은 #39의 P05를 pending으로 두고 있으며 마지막 갱신은 8월 23일이다. 한국어·아랍어 전체 실행과 영어 사전검증은 이후 자료에 더 자세하다. 그렇다고 P05 전체를 완료로 바꿀 수는 없다. 독립 운영·비교·영어 등 남은 조건을 나눠 적어야 한다.

`docs/requirements.md`의 구조화 사실·대체 이력·다국어 관련 요구사항은 pending인 반면 코드와 부분 검증이 존재한다. `docs/reports/README.ko.md`도 초기 r1/r2 안내 중심이다. **구현됨 / 내부 검증됨 / 독립 평가됨 / 제품 반영됨**을 별도 상태로 관리할 필요가 있다. 본 조사에서는 원래 상태 파일을 수정하지 않았다. [E15]

### 5.1 독립 기억 평가 설계

1. **사례 구성:** 한국어·영어·일본어의 신규 사실, 정정, 취소, 삭제 요청, 변화 없음, 복수 값 공존, 시간 경과, 재시작을 포함한다. 개발자가 사용한 템플릿과 최종 평가 사례군을 분리하고, 최종 사례는 개발 담당과 분리된 작성자가 각 언어로 새로 작성한다. 원어민 검수는 자연스러움과 정답 해석 가능성을 확인한다.
2. **표본 단위:** 기존 공개 평가 최소 조건인 사례 100개·서로 다른 사례군 100개, 언어당 30사례 이상을 출발점으로 삼는다. 반복 횟수를 독립 사례 수에 더하지 않는다. 실제 표본 수는 기존 검정력 도구와 개발용 파일럿으로 결정한다.
3. **표본의 한계:** 언어당 독립 사례 30개에서 실패가 0이어도, 독립 베르누이 시행을 가정한 단측 95% 실패율 상한은 약 9.5%다. “실패율 5% 미만”을 같은 방식으로 뒷받침하려면 실패 0건일 때 최소 59개가 필요하다. 이는 예시이며, 사례군 상관·여러 엔진 비교·실패 발생을 반영하면 더 큰 표본이 필요하다.
4. **동일 조건:** 같은 대화·질의·기억 토큰 예산을 사용하고 모델·임베더·추출기·버전을 기록한다. 정답·검색 위치 표시는 입력에서 제외한다. 우선 단순 벡터 검색과 Mem0 등 비교 가능한 경로를 확보하고, 엔진 고유 상태 노출 방식이 다른 경우 지표를 분리한다.
5. **판정:** current@1/@K, 오래된 사실 노출, 삭제 대상 재노출, 변화가 없는데 덮어쓴 비율을 공동 지표로 둔다. 사례군 단위 신뢰구간과 다중 비교를 적용한다. 오류는 추출 누락→동일 사실 식별→대체/보관 처리→영속화→검색→답변 단계로 나눈다.
6. **수정 규칙:** 개발용 실패로 수정한 뒤 최종 보유셋에서 한 번 판정한다. 실패를 확인한 보유셋은 다음 수정의 개발 자료가 되므로 새 최종 평가 자료를 확보한다. 현재 9사례는 회귀 테스트로 보존한다.

### 5.2 검색을 넘어 대화와 인지 기능의 효용 측정

공개 기준으로는 LongMemEval의 정보 추출·다중 세션·지식 갱신·시간 추론·답변 유보 항목을 활용할 수 있다. 공식 저장소는 500문항과 2025년 정제판, 2026년 V2 안내를 제공한다. 첫 재현은 데이터 revision을 고정한 정제판으로 시작하고, V2는 별도 프로토콜로 검토한다. 서로 다른 버전의 점수를 합치지 않는다. [LongMemEval 공식 저장소](https://github.com/xiaowu0162/LongMemEval)

제품에 맞춘 대화 평가에는 경험에서 생긴 선호, 이후 선호 변경, 특정 상황과 연결된 감정 기억, 언급하지 않는 편이 좋은 무관한 과거 기억을 추가한다. 인간 검토자는 기억의 정확성, 현재 질문에 대한 유용성, 불필요한 개입, 근거 없는 개인화를 평가한다. 합성 시간 이동으로 1·7·30·90·180일 조건을 빠르게 확인하되, 이를 실제 장기 사용자 관찰이라고 부르지 않는다.

비교군은 기억 없음, 같은 임베더의 단순 검색, Naia 전체 경로로 둔다. 이후 구조화 갱신·연관·감쇠·재생을 하나씩 제거해 어떤 기능이 이득과 오류를 만드는지 확인한다. 임베더 교체 효과와 기억 엔진 효과도 분리한다. 기억 엔진은 후보와 이력을 제공하고, 답변 생성·유보 판단은 에이전트 단계에서 평가한다.

승격 판단은 평균 답변 정확도만 보지 않는다. 최신 사실의 정답 개선과 함께 오래된 정보·삭제 대상의 사용, 입력/출력 토큰, 실제 모델 비용, 첫 답변까지의 지연을 확인한다. 기존 10만 건 surface p95 25ms·deep p95 100ms 목표는 해당 저장·검색 측정에 유지하고, 실제 임베딩과 최종 답변 지연은 별도 예산으로 관리한다.

### 5.3 압축·성능 실험의 실행 조건

압축은 동일 입력 창의 무압축·기본 요약·rolling summary·실제 LLM 요약을 비교한다. 출력 토큰 예산을 맞추고, 입력 안에 존재한 사실만 보존율 분모로 삼는다. 숫자·이름·시점·부정·취소 정보를 별도로 평가하며 요약 이후 답변 정확도, 새로 만든 사실, 원문과 반대인 사실도 기록한다. 보존율이 좋아도 환각이나 비용이 허용 범위를 넘으면 승격하지 않는다.

영어 성능 실험은 길이 버킷과 실제 텐서 배치를 개별 처리와 비교한다. 처리량 개선 최소 폭, 장문 품질 한계, 검색 비열등성 한계, 시간·디스크 예산을 실행 전에 정한다. 기존 7,168문서는 개발 자료로 두고 새 표본에서 판정한다. 최적화가 실패하면 현재 개별 처리를 기준으로 유지하고 전체 실행의 필요성을 다시 판단한다.

ANN은 10만 건 이상에서 exact 대비 품질을 확인하고, 구축 시간·색인 크기·RSS·동시 질의 p95를 함께 기록한다. 합성 영어와 한국어 통과를 모든 언어·실데이터 통과로 확대하지 않는다.

## 6. 단계별 실행 순서와 종료 기준

기간을 임의로 배정하지 않는다. 각 단계의 측정과 검토가 끝나면 다음 단계로 진행한다. Luna max가 구현하고 Astra가 설계 결정·구현·검증 결과를 검토하며, 부모 에이전트가 원시 결과를 독립 확인한다. 외부 검수나 모델 사용이 필요한 연구 때문에 즉시 가능한 로컬 성능 개선을 미루지 않는다.

| 단계 | 실행 | 다음 단계로 진행할 기준 |
|---|---|---|
| 1. 현재 기준 확인 | 기본·SQLite 검사 재실행, 병목 조사, 변경 전 소스와 측정 조건 고정 | 실패 원인과 개선 대상이 근거로 연결되고 Astra가 설계를 검토함 |
| 2. 국소 성능 개선 | 후보를 빠르게 검증하고 검색 결과·범위 격리·갱신 의미를 유지하는 변경 구현 | 정확성 회귀 검사 통과, Astra 구현 검토의 필수 수정 반영 |
| 3. 같은 조건에서 재측정 | 10만 건 이상에서 surface/deep를 구분한 반복 A/B, 자원·결과 동일성 확인 | 측정으로 효과가 확인되고 정확성 퇴행이 없음. 실패한 후보는 승격하지 않음 |
| 4. 다음 병목·기능 결함 | 측정 결과와 SQLite 미지원 기능의 영향을 기준으로 다음 한 가지 수정 선정 | 단계 1~3을 반복하고, 완료·미완료와 근거를 기록함 |
| 5. 독립 기억·대화 평가 | 독립 사례·검수·보유셋 확보, 기억 생명주기·실제 압축·대화 비교 | 언어별 결과·신뢰구간·실패 원인·토큰/비용·지연이 함께 보고됨 |
| 6. 제품 후보 판단 | 재시작·갱신·삭제·격리·배포 패키지 연결 및 성능 회귀 확인 | 지원 범위와 출시 후보 판단, 남은 연구 과제가 근거와 연결됨 |

각 실험은 새 측정값, 판정에 영향을 주는 실패 분석, 또는 실행을 막는 결함의 해소 중 하나를 남겨야 한다. 새로운 사례와 결과가 나오지 않는 상태에서 평가 도구 확장만 반복되면 범위를 줄이고 자료 확보에 우선순위를 돌린다.

이 계획의 완료는 “모든 경쟁 엔진보다 우수”가 아니다. **지원하는 제품 경로가 재현되고, 기억 기능의 이득과 실패가 독립 사례로 수치화되며, 어떤 기능을 출시하고 무엇을 연구로 남길지 근거 있게 결정할 수 있는 상태**를 완료 기준으로 삼는다.
