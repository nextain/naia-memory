# 검색 성능 벤치마크 — 2026-07-04

naia-memory의 SqliteAdapter(고성능 경로)가 10만 사실 규모에서 실제로 얼마나
빠른지, 그리고 그 지연이 어디서 나오는지를 측정했다. 결론부터 말하면 두 가지
지연 목표는 이미 충족되어 있고, deep recall을 4배 빠르게 만들 여지가 하나 있지만
그것을 반영하려면 검색 품질을 먼저 실제 임베딩으로 검증해야 한다.

## 무엇을 측정했나

기존 스트레스 테스트(`src/__tests__/stress-test-tiered-100k.ts`)는 쿼리 두 개를
한 번씩만 재보고 "25ms 미만"이라고 판정했다. 워밍업도 없고, 표본도 하나고,
deep recall은 아예 재지 않았다. 그래서 통계적으로 견고한 하네스를 새로 만들었다
(`src/benchmark/perf/run-latency.ts`).

핵심 설계 하나: 임베딩 비용과 검색 비용을 분리했다. 실제 transformer로 10만 개를
임베딩하면 CPU에서 54분이 걸려 반복 실험이 불가능하다. 그런데 sqlite-vec는
브루트포스 선형 스캔이라 지연이 벡터의 *값*이 아니라 (차원 수, 코퍼스 크기)에만
의존한다. 그래서 즉시 계산되는 결정론적 임베더(`deterministic-embedder.ts`)로
임베딩을 대체해도 검색 지연은 실제와 동일하게 대표성을 갖는다. 주입이 54분에서
1분으로 줄었고, 이것이 측정→개선 루프를 가능하게 한 열쇠다.

## 현재 도달점 (10만 사실, 표본 300회, 384차원)

Surface recall(자주 쓰는 hot 1만 개만 검색)은 중앙값 4.0ms, 95퍼센타일 5.3ms다.
25ms 목표를 크게 밑돈다.

Deep recall(전체 10만 개 스캔)은 중앙값 40.7ms, 95퍼센타일 43.8ms다. 100ms
목표는 통과하지만 surface보다 정확히 10배 느리다. 코퍼스가 10배 크니 예상대로다.

주입 처리량은 초당 1631건, 상주 메모리 288MB, DB 파일 196MB.

## deep recall 41ms는 어디서 나오나

계측 결과(`breakdown.ts`) 41ms의 99%가 sqlite-vec 브루트포스 벡터 스캔 한 곳에서
나온다. 구체적으로 벡터 스캔 39.0ms, FTS 키워드 0.1ms, id 매핑 0.14ms, 최종
SELECT 0.13ms, 워커 프로세스 간 통신 오버헤드는 약 1.3ms에 불과했다.

이는 원래 의심했던 "워커 통신 왕복이 병목"이라는 가설을 기각한다. 통신은 거의
공짜다. 느린 건 순수하게 10만 개 × 384차원 float32 거리 계산이다.

## 4배 빠르게 만들 여지 (단, 품질 검증 선행)

이진 양자화(binary quantization)를 시험했다(`probe-binary-quant.ts`). 벡터를
비트로 압축해 Hamming 거리로 1차 후보를 추리면 2ms 만에 끝난다(16배). 이것만으로는
정확도가 떨어지지만, 이진으로 상위 100개를 추린 뒤 그 100개만 원본 float로 다시
정렬하는 2단계 방식을 쓰면 8.6ms에 원본 상위 10개를 100% 복원했다. 34ms → 8.6ms,
약 4배다.

**그러나 이 100% 복원 수치는 그대로 믿으면 안 된다.** 결정론적 임베더의 벡터는
의미 구조가 없어 이진 양자화의 손실을 재는 데 부적합하다. 실제 임베딩에서는 이진
양자화가 상위 결과를 얼마나 보존하는지 다시 측정해야 하고, 그 검증 없이 어댑터에
반영하면 지연을 줄이려다 검색 품질을 희생하는 과적합이 된다. 그래서 이 최적화는
"실제 코퍼스 recall 검증" 뒤로 게이트를 걸어 둔다.

## 재현

```bash
npx tsx src/benchmark/perf/run-latency.ts        # 지연·정확도 벤치 → reports/perf/*.json
npx tsx src/benchmark/perf/breakdown.ts          # deep recall 단계별 귀속
npx tsx src/benchmark/perf/probe-binary-quant.ts # 이진 양자화 최적화 프로브
```

환경변수: `BENCH_COUNT`(기본 10만), `BENCH_SAMPLES`(기본 300), `BENCH_TOPK`(기본 10),
`BENCH_DIMS`(기본 384), `COARSE`(프로브 후보 수, 기본 200).

## 한계 (정직하게)

정확도(precision@k) 수치는 합성 코퍼스에서 숫자 토큰 접두어가 충돌해 오염되므로
믿을 수 없다. 이 벤치는 오직 *지연*만 신뢰할 수 있는 산출물이다. 기억 품질과
정확도는 실제 임베더 + 라벨 코퍼스로 재는 별도 축(축 B)에서 다뤄야 한다.
