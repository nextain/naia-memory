# 기억 품질 벤치마크 — 2026-07-04

성능(지연)이 아니라 naia-memory가 기억을 얼마나 잘 담아두고 꺼내는지, 그리고 대화
컨텍스트를 얼마나 잘 압축하는지를 측정한다. 둘 다 외부 API 없이 로컬에서 돈다.

## 1. 실시간 컨텍스트 압축 (compact)

`compact()`는 대화가 길어져 LLM 컨텍스트 한도에 가까워질 때 앞부분을 요약문으로
갈아끼우는 기능이다. 82개 메시지 대화에 사실 10개(강아지 이름, 알레르기, 마감일
등)를 흩어 넣고, 앞 74개를 압축한 뒤 두 가지를 쟀다. 압축률(요약 토큰 ÷ 원본 토큰)과
충실도(원래 진술한 사실 10개 중 몇 개가 요약에 살아남았나).

기본 경로(요약 LLM 없는 결정론적 recap)는 토큰을 4분의 1로 잘 줄이지만 사실의
70%를 잃는다. 마감일, 알레르기, 이사 계획 같은 중간에 진술된 사실 일곱 개가 요약에서
사라졌다. recap이 첫 사용자 발화를 "목표"로, 첫·끝 문장을 인용으로, 대문자 토큰을
"주제"로만 보존하는 휴리스틱이라 그렇다.

세션 아이디를 넘겨 rolling-summary 경로를 태우면, 처음 측정에서는 **압축률이
162%였다 — 요약이 원본보다 커졌다.** 원인은 압축 스템(stem)이 메시지가 하나
밀려날 때마다 그 메시지 요약 블록을 계속 덧붙여 무한히 자라던 데 있었다. 이를
누적 다이제스트(밀려난 메시지 수 + 가장 오래된 한 문장)로 바꿔 고쳤고, 지금은
압축률 29.7%로 내려가 실제로 3배 넘게 압축한다(충실도 50%). 이 수정은
`src/memory/index.ts`의 `updateRollingSummary`에 있고, 유닛 372개 전부 통과한다.

충실도를 더 끌어올리려 했으나, 시스템의 importance 점수가 사실 문장("강아지
이름은 Rex")과 잡담("그래서 다음은?")을 구분하지 못했다(둘 다 같은 점수). 대문자
토큰 같은 키워드로 사실을 집으면 이 합성 코퍼스에만 맞는 과적합이 된다. 그래서
결정론 경로의 충실도 한계는 근본적이라 결론짓고, 고충실도가 필요하면 LLM
요약기를 붙이는 것이 정도(正道)라는 것을 데이터로 확인했다(억지 개선 안 함).

요약 LLM을 붙이면(여기서는 사실을 추출하는 목(mock)으로 모사) 충실도 90%에
압축률 16.5%로, 둘 다 가장 좋다. 기본 30%와 LLM 90% 사이의 간극이 곧 요약 LLM이
주는 값이다.

재현: `npx tsx src/benchmark/quality/compact-bench.ts` → `reports/quality/compact-compression.json`

## 2. 검색 품질 (recall@k) — 그리고 이 지표가 왜 이 코퍼스에 안 맞는가

한국어 fact-bank(200개 사실)를 로컬 multilingual-e5-large로 임베딩하고, 라벨된
질문 172개에 대해 정답 사실이 상위 몇 위에 오는지 쟀다. 결과는 낮았다 — 벡터 전용
모드에서 recall@10이 21.5%, RRF 모드에서 8.7%.

낮은 수치를 그대로 믿지 않고 원인을 파고들었다. 정답 사실의 순위를 직접 계산해 보니
**질문이 사실과 직접 맞닿을 때는 검색이 완벽하게 동작한다.** "음주 여부 관련해서
기억나는 거 있어?"는 "술은 안 마셔"를 1위로 정확히 찾는다. 문제는 라벨이었다.
"취미 뭐야?"의 정답 라벨은 "한 달에 책 2권 읽어"인데, 검색 1위는 "요리 취미야"로
오히려 더 잘 맞는 사실이었다. "알레르기 있어?"의 정답 라벨은 엉뚱하게 "약은 아침에
먹어"였다.

즉 fact-bank v2의 질문→정답 라벨은 하나의 정답 사실을 꼭 집어 꺼내는
retrieval 평가용이 아니라, 검색된 맥락으로 LLM이 답을 제대로 하는지를 보는
답변평가(LLM-judge)용이다. 그런 라벨에 recall@k를 들이대면 검색 품질을 구조적으로
과소평가한다. **이 코퍼스에는 recall@k가 맞지 않는 지표다.** 답변 품질은 LLM-judge
경로(aihub141 / phase-b, GEMINI 키 필요)로 재는 것이 옳다.

한편 같은 라벨을 두 모드가 똑같이 보므로 상대 비교는 유효하다. **한국어에서는 벡터
전용이 RRF보다 recall@10 기준 2.5배 낫다(21.5% 대 8.7%).** 이를 파고들다 별도
결함 하나를 찾아 고쳤다. RRF 모드가 정확 엔티티 매치와 지식그래프 활성 보너스(eb)를
점수에 아예 반영하지 않고 있었다 — 벡터 전용 모드만 그 보너스를 쓰고 있었다. 그래서
질문에 정확히 등장하는 엔티티로 회상할 때조차 RRF가 벡터 전용보다 나빴다. 보너스를
RRF 점수에도 더하도록 고치니(`src/memory/adapters/local.ts`), 엔티티 정확 매치
회상이 두 배로 올랐다(단일-정답 프로브에서 recall@1 2.9%→5.3%).

다만 그 수정만으로 벡터 전용을 따라잡지는 못한다. 남은 격차는 RRF의 순위 융합
방식(K=60) 자체가 벡터 유사도의 분별력을 눌러버리는 데서 온다. 차원이 작은 의미
임베더에서 기본을 벡터 전용으로 돌리거나, 순위 융합 대신 점수 융합을 쓰는 것을
검토할 근거다 — 다만 이는 검색 동작을 폭넓게 바꾸므로 별도로 범위를 잡아 clean
코퍼스나 LLM-judge로 검증한 뒤 진행해야 한다.

덤으로 확인한 것: e5는 문서에 "passage:" 접두어를 붙여야 한다는 규약이 있는데,
어댑터는 저장 시 "query:" 접두어를 쓴다. 이게 문제일까 싶어 두 방식의 정답 순위를
비교했더니 "passage:" 쪽이 오히려 약간 나빴다. 접두어 규약 위반은 이 경우 원인이
아니었다 — 가설을 측정으로 기각했다.

재현: `npx tsx src/benchmark/quality/recall-at-k.ts` (환경변수 `BENCH_CATEGORY`,
`RUN_BINQUANT`, `WITH_DISTRACTOR`) → `reports/quality/recall-at-k.json`

## 정직한 한계

- recall@k 절대값은 위 라벨 성격 때문에 검색 품질의 하한도 아니다. 인용 금지.
- 유효한 결론은 세 가지다. 검색은 직접 질문에서 정상 동작한다. 한국어에서 벡터
  전용이 RRF보다 낫다. 이 코퍼스의 답변 품질은 LLM-judge로 재야 한다.
- 장기 기억의 인지적 속성(감쇠 곡선, 재응고, consolidation, 무의식적 spike)은 아직
  벤치가 없다 — 다음 루프 후보.
