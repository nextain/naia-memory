# 명시적 삭제 요청이 기억에 반영되지 않는 원인

2026-09-15 · candidate-az1 실행 뒤 오프라인 분석 · 유료 호출 없음

## 요약

"기억에서 지워 줘"처럼 사용자가 명시적으로 삭제를 요청하면, 추출 모델은 삭제 연산을 제대로 만들어 냅니다. 그런데 제품의 삭제 근거 검증이 그 연산을 거부하고, 추출기는 거부 사실을 알리지 않은 채 그 삭제 연산을 버립니다. 그래서 삭제 검증기까지 가지 못하고, 지우라고 한 사실은 활성 상태로 남습니다. 모델을 바꿔도 같은 결과가 나오는 제품 경로의 결함입니다.

## 관찰

candidate-az1 에서 명시적 삭제 요청 6건(ko/en/ja-05, ko/en/ja-14) 중 5건의 대상 사실이 활성 상태로 남았습니다. 나머지 en-05 는 사실이 하나도 저장되지 않았지만, 원문 에피소드가 검색되면서 삭제된 비밀이 답변에 다시 나왔습니다. 삭제 검증기는 실행 전체에서 두 번만 불렸고, 두 번 모두 "월요일 수업은 취소해"류의 취소 사례(en-06, ja-06)였습니다.

candidate-az1 은 추출 응답 원문을 보존하지 않았습니다. 그래서 같은 사례를 Gemini flash-lite 로 돌린 9월 5일 첫 실행의 영수증에서 추출 응답 원문을 꺼내 제품의 근거 검증 규칙에 대입했습니다. 영수증 위치는 `.tmp/naia-memory-quality-20260906/.../runs/actual-20260905T184756Z-17f137/receipts.jsonl` 입니다.

|---|---|---|---|---|---|
| ko-05 | delete | 창고 출입 암호 | 달빛상자 | 없음 / 없음 | 거부 |

en-05, ja-06, ko-06 의 첫 실행 응답은 JSON 이 깨져 있어 대조할 수 없었습니다.

## 원인

`src/memory/delete-grounding.ts` 의 `hasGroundedDeleteEvidence` 는 삭제 연산에 다음을 모두 요구합니다.

1. 근거 인용문이 발화 전체와 정확히 같을 것
2. 대상 인용문이 발화 안에 있을 것
3. 주어·속성·값이 모두 문자열로 있고 극성이 affirmed 일 것
4. **대상 인용문이 값을 포함하거나, subjectId 와 propertyId 가 둘 다 있을 것**

명시적 삭제 요청은 거의 항상 값을 말하지 않습니다. "암호 값을 다시 알려 주지 마"라고 지시하는 사례도 있습니다. 그래서 4번은 id 가 있어야만 통과하는데, 모델은 두 실행 모두 id 를 비워 두었습니다. 취소형 사례(en-06)는 대상 인용문에 값이 들어가거나 모델이 id 를 채워 통과했습니다.

거부된 뒤의 처리가 더 문제입니다. `src/memory/llm-fact-extractor.ts` 는 사실마다 도는 `flatMap` 안에서, 삭제 연산의 근거 검증이 실패하면 그 연산을 `[]` 로 바꿔 버립니다. 같은 발화의 다른 사실은 남지만 삭제 연산은 흔적 없이 사라집니다. 실패 코드도, `onFailure` 호출도 없습니다. 벤치마크는 추출 실패 0 으로 기록했고, 사용자는 삭제가 됐다고 믿게 됩니다.

## 이 분석이 말하는 것과 말하지 않는 것

말하는 것: 두 모델(Gemini flash-lite, gpt-5-4-nano)에서 명시적 삭제 요청이 같은 방식으로 실패했고, 첫 실행 응답으로 거부 지점을 규칙 단위로 특정했습니다. 취소형은 통과하고 명시적 삭제형은 거부되는 차이도 규칙으로 설명됩니다.

말하지 않는 것: nano 응답이 첫 실행과 똑같은 모양이었다는 것은 원문이 없어 확인하지 못했습니다. 결과(검증기 호출 2회, 대상 사실 활성)가 같다는 것만 확인했습니다. en-05 에서 사실이 하나도 저장되지 않은 현상은 이 폐기 경로로 설명되지 않습니다(폐기는 삭제 연산 하나만 없앱니다). 첫 실행의 en-05 응답은 JSON 이 깨져 대조할 수 없었습니다. candidate-az2 는 추출 응답 원문을 보존하므로 두 가지를 거기서 확정합니다.

## 수정 후보

각각 새 run id 로 측정합니다. 결과를 본 뒤 기존 사례나 기준을 고치지 않습니다.

1. **조용한 폐기를 없앤다.** 근거 검증 실패를 `semantic-rejection` 같은 형식화된 실패로 `onFailure` 에 알린다. 다른 사실을 버리지 않는 현재 동작은 유지한다. 동작이 가장 적게 바뀌고 관측성이 바로 생긴다.
2. **삭제 연산에 안정 식별자를 요구하도록 추출 프롬프트·스키마를 고친다.** 삭제형에서 subjectId·propertyId 를 필수로 적게 한다. 규칙은 그대로 두고 모델 출력을 규칙에 맞춘다.
3. **대상 인용문이 주어와 속성을 가리키면 값 없이도 통과시키는 규칙을 검토한다.** 오삭제 위험이 커지므로 삭제 검증기의 독립 판정이 그 위험을 받아낸다는 조건과 함께 적대 검토가 필요하다.
4. **검증된 삭제의 원문 에피소드를 최신 검색에서 제외한다.** en-05 처럼 사실이 없어도 원문이 새는 경로를 막는다. 보존 우선 원칙에 따라 지우지 않고 보관 상태로 둔다.

오프라인 회귀 기준: 첫 실행 응답 5건과 명시적 삭제 사례 6건에서, 1번 적용 후 실패가 형식화돼 드러나는지, 2번 적용 후 삭제 검증기까지 도달하는지.

## 검토 정정

1차 검토 의견은 폐기 범위를 "그 발화의 사실 배열 전체"로 적었습니다. 코드를 다시 읽어 보면 폐기는 사실마다 도는 `flatMap` 안에서 일어나므로, 없어지는 것은 거부된 삭제 연산 하나입니다. 이 문서는 코드 기준으로 적었습니다.
