# az4 결과: 명시적 삭제 요청 9건 중 7건이 사실에 반영되었다

az4는 az5b와 같은 재생 추출 위에 삭제 규칙 두 가지를 더해 측정했다(제품 148907f).

- 값을 말하지 않은 명시적 삭제 요청이라도 대상 인용문에 속성 이름이 들어 있으면 근거로 인정한다.
- 구조 없이 저장된 사실은 삭제 연산과 내용이 정확히 같을 때만 후보로 올린다.

유효 조건은 모두 통과했다. 추출 재생 42/42, 실제 추출 호출 0건, 삭제 검증 호출 정확히 7건이다. 사실 상태 판정은 점수를 열기 전에 커밋했다(`fact-state-judgement.md`, bcf44a4).

## 1차 지표: 삭제의 사실 상태

gold에서 지워져야 할 명제가 있는 9사례(05·06·14 계열) 가운데 대상 사실이 archive된 사례는 az5b 3건에서 az4 7건으로 늘었다. 잘못된 archive는 0건이다. 사전 등록한 예측은 사실 상태에서 모두 맞았다.

- 검증기에 도달한 사례와 경로 태그가 예측과 같았다. 새로 도달한 사례는 ko-05·ja-05(문자열 일치)와 ko-14·ja-14(속성 이름 근거)다.
- 후보는 사례마다 1개였다.
- 검증기(deepseek-v4-flash)는 7건을 모두 승인했다.
- 남겨야 할 사실은 모두 활성으로 남았다. 다른 프로젝트의 채널과 형식, ko-05의 두 번째 메모 사실, 06 계열의 남길 수업이 여기에 해당한다.
- 대체로 인한 은퇴 목록은 az5b와 같았다.

남은 2건은 추출 쪽 원인이다.

- en-05: 사용자가 "값을 다시 말하지 말라"고 했는데 추출기가 그 값을 대상 인용문으로 적었다.
- en-14: 추출기가 속성 이름을 "status-report-day"로 정규화해 인용문에 글자 그대로 들어 있지 않았다.

추출 프롬프트를 바꾸면 재생이 깨지므로 az4 범위 밖이다.

## 편차

capture-meta의 extractionFailures 2건은 추출 호출 실패가 아니다. 진단 커밋(cb0f19e)이 거부된 삭제 연산을 실패 콜백으로 보고한 것으로, `delete-ungrounded` 코드의 en-05와 en-14다. 사전 등록에 적지 않은 집계 방식이다. 재생 실행이라 실제 추출 호출이 0건이므로 추출 게이트는 해당 없음(N/A)이어야 한다. 그런데 score가 이 2건을 세어 최대치 2에서 PASS를 찍었다. 우연히 임계값에 걸린 값이므로 이 보고서는 추출 게이트를 N/A로 적는다. 다음 러너부터는 `delete-ungrounded`를 별도로 세고, 재생 실행의 추출 게이트를 N/A로 계산하도록 사전 등록에 넣는다.

## 답변 수준 (기술만, 귀속하지 않음)

사전 등록에서는 삭제 누출이 줄지 않는다고 예측했는데, naia 팔에서 4건(ko-14, en-05, en-14, ja-14)이 3건이 되어 ja-14가 빠졌다. ja-14 행의 검색 맥락에는 원문 에피소드를 통해 값("音声")이 여전히 들어 있었고, 답변 모델이 "지웠으므로 기억하지 않는다"고 답했다. ko-14는 같은 조건에서 값을 말했다. 에피소드가 값을 계속 공급한다는 사전 등록의 기전은 두 행 모두에서 확인되었다. 이 1건의 차이는 az5에서 잰 답변 노이즈(맥락이 같은데 답변이 바뀐 행이 13/57) 범위 안이므로 규칙 효과로 읽지 않는다.

naia 팔의 현재 정답은 43/45(az5b 42), 전체 50/57(47)이었다. 게이트는 여전히 FAIL이다. 삭제 누출 3건, false_overwrite 3건, critical_reversal 1건이다. false_overwrite 3건 가운데 ko-14는 사실이 archive된 행이라 덮어쓰기가 아니다. 판정 모델이 삭제를 덮어쓰기로 읽는 혼동이 az1·az2에 이어 다시 나왔으므로 `run/reviewer-disputes.json`에 이의로 올렸다. 이 행을 빼면 2건(en-14 삭제 미반영, ja-10 실제 오대체)이다. 원문 에피소드가 삭제된 값을 계속 공급하는 한 삭제 누출은 답변 수준에서 사라지지 않는다. 다음 단계인 에피소드 필터 재측정이 이 문제를 다룬다.

## 범위와 한계

- 휴리스틱 모순 필터 경로와 합성 42사례에서만 확인했고, 판정자는 작성자 한 명이다.
- 검증기에 도달한 7건은 모두 후보가 1개였다. 검증기는 여러 후보 중 하나를 고르는 과제를 받지 않았다. 형제 값이 둘 이상이면 규칙이 검증기 전에 거부하도록 설계했기 때문이다. 따라서 여러 후보 중에서 고르는 검증기의 정밀도는 이 실행으로 확인되지 않았다.
- 속성 이름 근거는 인용문에 라벨이 글자 그대로 들어 있어야 한다. 추출기가 라벨을 정규화하면 동작하지 않는다(en-14).
- 근거 검증은 id가 비어 있지 않은지만 본다. ko-05·ja-05는 잘못 붙은 `preference:tool`로 근거를 통과했다. az4에서는 이 id를 후보 선정에 쓰지 않았지만 약점은 남아 있다.
- 문자열 후보는 사실 내용(비밀 값 포함 가능)을 검증기에 보낸다. 삭제 연산에도 이미 그 값이 들어 있다.
- 제품 기본 설정의 삭제 검증기는 클라우드 gemini-2.5-flash다(`llm-delete-verifier.ts`). 기본 설정에서는 사실 텍스트가 클라우드로 나가며, 추론을 로컬에 두라는 지침과 충돌한다. az4와 별개로 결정이 필요한 항목이다.
- 후속 과제는 둘이다. 형제 값이 검색 상위 결과 밖에 있어도 차단되는지 확인하는 consolidation 수준 회귀 테스트를 추가해야 한다. 태그 우선순위 주석을 바로잡아야 한다(sources 배열로 바꾸는 방법).
