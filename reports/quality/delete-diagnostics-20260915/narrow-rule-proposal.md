# 값 없는 명시적 삭제를 통과시키는 좁은 규칙 — 적대 검토용 제안

2026-09-15 · 코드 변경 전 제안 · 브랜치 feat/delete-grounding-diagnostics

## 문제

`hasGroundedDeleteEvidence` 의 마지막 조건은 "대상 인용문이 값을 포함하거나, subjectId 와 propertyId 가 둘 다 있을 것"입니다. 사용자가 "창고 출입 암호를 지워 줘, 값은 말하지 마"라고 하면 대상 인용문에 값이 없고, 모델은 id 를 비워 두어 삭제가 거부됩니다. 9/5 Gemini 응답 재생에서 명시적 삭제 5건이 모두 이 조건 하나로 거부됐습니다. 해당 사실은 활성 상태로 남습니다.

## 현재 삭제 경로 (코드 기준)

1. 추출기가 delete 연산을 냅니다. 근거 인용문은 발화 전체, 대상 인용문은 발화의 부분문자열, structured 에 주어·속성·값·극성이 들어갑니다.
2. `hasGroundedDeleteEvidence`(추출 시)와 `hasGroundedDeleteAuthority`(consolidation 시, 같은 규칙)가 근거를 검사합니다.
3. `resolveDeleteTarget` → `eligibleCandidates`: id 가 없으면 `findStructuredDeletionTargets`(구조화 사실의 정확 일치)만 후보가 되고, id 가 있으면 같은 정체성(subjectId+propertyId) 후보와 같은 값 후보가 더해집니다. 후보가 32개를 넘으면 거부합니다.
4. 독립 삭제 검증기(다른 모델 계열)가 발화와 후보를 보고 `authorized` 와 대상 id 를 고릅니다.
5. 승인되면 대상 사실을 `archived`, `validTo=now` 로 바꿉니다. 물리 삭제는 없습니다.

## 제안 (좁은 규칙)

마지막 조건을 다음처럼 바꿉니다.

> 대상 인용문이 값을 포함하거나, subjectId 와 propertyId 가 둘 다 있거나, **대상 인용문이 structured.property 를 포함하고(정규화 후 부분문자열) 증거 종류가 explicit_removal_request 일 것**.

나머지 조건(발화 전체 인용, 대상 인용문이 발화의 부분문자열, 주어·속성·값 문자열, 극성 affirmed, 사용자 발화)은 그대로 둡니다. 3번의 후보 선정과 4번의 검증기는 바꾸지 않습니다. 즉 새로 통과한 연산도 **structured 가 기존 활성 사실과 정확히 일치해야 후보가 생기고, 검증기가 승인해야 보관 처리**됩니다.

재생 사례에 대입하면 이렇습니다.

- ko-05: 대상 "창고 출입 암호" ⊇ 속성 "출입 암호" → 통과
- ko-14: "솔 프로젝트의 배포 채널" ⊇ "배포 채널" → 통과
- en-14: "Project Kite's reporting day" ⊇ "reporting day" → 통과
- ja-05: "合言葉" ⊇ "合言葉" → 통과
- ja-14: "波企画の配信形式" ⊇ "配信形式" → 통과

## 검토해 주실 위협 (범위 제한)

이 제안이 막아야 하는 것은 **사용자가 요청하지 않은 사실의 보관 처리(오삭제)** 하나입니다. 보존 우선 원칙상 보관은 되돌릴 수 있지만, 최신 회상에서 사라지므로 사용자 입장에서는 기억을 잃은 것과 같습니다.

- 모델이 structured 의 값을 다른 사실의 값으로 지어내 엉뚱한 사실을 맞추는 경우
- 같은 속성의 사실이 여러 개(프로젝트별, 복수 값)일 때 잘못된 쪽을 지우는 경우(ko-14/en-14/ja-14 가 바로 이 형태: 다른 프로젝트는 남겨야 함)
- 대상 인용문이 속성 이름만 가리키는 짧은 요청("알레르기 지워")으로 복수 사실이 한꺼번에 후보가 되는 경우
- 인용·가정·타인 발화 안의 삭제 표현
- 검증기가 실패하거나 없는 환경(현재는 거부로 닫힘)

검토 범위 밖(이미 받아들인 것): 물리 삭제 없음, 검증기 독립성 자체의 품질, 원문 에피소드 노출(별도 결정 항목).
